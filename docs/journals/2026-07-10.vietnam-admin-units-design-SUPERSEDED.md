# Design: `vietnam-admin-units` — a time-versioned Vietnam administrative-unit gazetteer

Written 2026-07-10. Brainstormed design for a new foundation layer beneath the
election projects. Terminal step of this doc: an implementation plan (writing-plans).

## Why this exists

Every hard problem in `vietnam-elections-wikidata` traces down the same
dependency chain to one missing foundation:

```
NA members (P39, per term)
   └─ depend on → electoral units (per session/term; split on namespace change)
         └─ depend on → administrative units (province / district / commune-ward, per reform era)
               └─ depend on → time (which reform generation: pre-2025 vs post-2025)
```

The symptom is visible in `vietnam-elections-wikidata/reference/lao-cai-unit-1-parts.md`:
its "WD P131 now" column, the ⚠️ "Wikidata is mid-migration" warning, stale
huyện parents (`Q8052180`/`Q6695817`), `P31` still reading "commune" where
Resolution 85 says *phường*, and "huyện Trấn Yên (inferred)" — none of that is
electoral-unit work. It is **administrative-unit work leaking upward**, hand-
maintained in a document that should only describe one electoral unit's parts.

The existing `vietnam-elections/.../localities.json` does not fill the gap: it is
a flat, per-cycle snapshot (province names only, local `loc-` ids, no QIDs, no
hierarchy, no time-versioning). Neither app repo owns a clean administrative
layer. This project builds it.

## Decisions locked during brainstorming (2026-07-10)

1. **Source of truth = local model, and it also drives Wikidata.** A repo-owned,
   versioned dataset is authoritative even where Wikidata is stale; it is *also*
   the batch source for pushing corrections upstream. (Not "just fix WD," not
   "crosswalk-only.")
2. **Its own submodule/repo.** Proposed name **`vietnam-admin-units`** (kebab-
   case, mirrors sibling repos; final name confirmable). It is a reusable
   reference dataset independent of elections, justifying separation.
3. **Complete gazetteer, all tiers** (province → district → commune/ward),
   feasible because there is an authoritative machine-readable upstream:
   - GSO/NSO *danh mục hành chính* service: `https://danhmuchanhchinh.nso.gov.vn/DMDVHC.asmx`
   - GSO change history: `https://danhmuchanhchinh.nso.gov.vn/Lich_Su_Moi.aspx`
   - Community packages built on the above (e.g. `vietnam-provinces` on PyPI).
4. **Temporal model = entity + validity + lineage** (not snapshot-per-era, not
   pure event-sourcing). Snapshots and the change-history are *inputs*; the
   entity graph is the source of truth. See Data model.
5. **District (huyện) tier is first-class**, modeled with `valid_to` = 2025
   reform date and successor edges — matching how Wikidata keeps abolished huyện
   items as former entities, and keeping district-composed pre-2025 electoral
   units cleanly expressible.

## Scope

**In scope:** administrative geography of Vietnam over time — provinces,
districts, communes/wards — with existence spans, parent-at-time hierarchy,
lineage across reforms, and `mã ĐVHC ↔ Wikidata QID` reconciliation.

**Explicitly out of scope (stays up-layer):** any election, electoral-unit,
candidate, or member concept. This layer holds **zero** election concepts.

## Architecture

```
vietnam-admin-units  (NEW — layer 1: the gazetteer)
        ▲                    ▲
        │                    │
vietnam-elections     vietnam-elections-wikidata
 (layer 2/3 consumer)   (layer 2/3: units + members → WD)
```

## Data model

One record per real-world admin unit, per era of existence:

| field | purpose | Wikidata target |
|---|---|---|
| `local_id` | stable, repo-owned spine (survives GSO code reuse) | — |
| `gso_code` | official mã ĐVHC (time-scoped; may be reused across reforms) | code prop if one exists |
| `wikidata_qid` | reconciled item | the item |
| `name_vi`, `type` | tỉnh / huyện / xã / phường / … | label, P31 |
| `parent` | parent unit **at time** | P131 (+ time qualifier) |
| `valid_from` / `valid_to` | existence span | P571 / P576 |
| `merged_into` / `split_from` / `replaces` | lineage edges | P7888 / P1365 / P1366 |
| `source` | GSO snapshot date + Nghị quyết reference | reference |

**Identifier subtlety:** GSO `mã ĐVHC` codes are reused/reassigned across
reforms, so they are *not* stable across eras. A repo-owned `local_id` is the
spine; `gso_code` is a time-scoped attribute. This is the same "namespace
change" lesson `vietnam-elections-wikidata`'s electoral-unit journal
(`2026-07-09.01`) learned, applied one layer down.

The entity graph maps almost one-to-one onto Wikidata's single-item-per-unit
model (P571/P576/P7888/P1365/P1366/P131-with-time), which is what makes "fix
Wikidata" a generated *output* rather than manual editing.

## Ingestion & reconciliation pipeline

Mirrors the existing `vietnam-elections-wikidata` pattern
(`reconcile.py` → `prepare.py` → `upload.py`):

```
GSO danh mục (current snapshot)  ─┐
GSO Lịch_Sử (change history)      ─┤→  ingest/normalize → entity graph (SoT, versioned JSON)
historical snapshots / packages  ─┘         │
                                            ▼
                                reconcile to QID (code + name-fold + parent-at-time + era)
                                            │
                                            ▼
                           ┌─ export: clean query API for layers 2/3 (JSON)
                           └─ export: QuickStatements/API batch to FIX Wikidata
```

1. **Ingest** — pull GSO current + `Lịch_Sử` + historical snapshots into a
   committed raw cache (reproducible; avoids hammering a government endpoint).
2. **Build graph** — diff snapshots and apply change-events to produce the
   entity + validity + lineage model. Change-events *derive* lineage edges
   instead of the name-inference the lao-cai file resorts to.
3. **Reconcile** — match each entity to a QID by code, name-fold, and
   parent-at-time. Output the `mã ĐVHC ↔ QID` map — the artifact
   `vietnam-elections-wikidata` currently hand-builds.
4. **Emit** — (a) a clean consumer export; (b) a Wikidata correction batch (the
   stale-P131/P31 fixes flagged in the lao-cai file become generated output).

## How layers 2/3 consume it

- `vietnam-elections-wikidata`: electoral-unit `P527` parts and the old↔new
  crosswalk come from *querying this graph*; the lao-cai `reference/*.md` files
  become generated/verified against layer 1 rather than hand-maintained.
- `vietnam-elections`: per-cycle `localities.json` can be regenerated by slicing
  the graph at the election date, yielding real QIDs and hierarchy instead of
  flat `loc-` names.

## First implementation milestone (scaffold + de-risk the source)

The full data model above assumes GSO exposes usable snapshots *and* change-
history. Validate that before building on it. First slice is exactly:

1. **Create the submodule/repo** `vietnam-admin-units`, wired into the monorepo
   `.gitmodules`, with README + AGENTS.md stub mirroring sibling repos.
2. **Set up `docs/journals/`** in the new repo, following the established
   decision-journal convention.
3. **Explore the GSO endpoints** (`DMDVHC.asmx`, `Lich_Su_Moi.aspx`, and the
   `vietnam-provinces` package) and **document, in a journal, what is actually
   available**: request/response shapes, whether point-in-time snapshots are
   retrievable, whether the change-history is machine-readable and carries
   effective dates + decision references, code stability/reuse behavior, and
   coverage of the district tier.

The findings from step 3 feed the next spec/plan iteration (the ingest → graph →
reconcile → emit build), which may adjust the temporal model if the source
differs from assumptions.
